# Релизы и обновления десктопа

## Управление через админку

Войдите во frontend с ролью `administrator` и откройте Admin → «Сборки десктопа».
Для существующего Keycloak нужны audience `revex-api` и realm-роли в claim `roles`
для клиента `revex-frontend` (см. `Keycloak/README.md`).

1. Скачайте артефакт Actions `RevEx-Desktop-win-x64-<version>` для Windows или `RevEx-Desktop-macos-<version>` для обеих архитектур macOS. Отдельные `osx-x64` и `osx-arm64` тоже доступны.
2. Распакуйте внешний ZIP GitHub и выберите внутренний ZIP-комплект релиза.
3. Нажмите «Загрузить и проверить». Релиз появится как черновик.
4. Выберите релиз, нужную платформу и нажмите «Опубликовать и включить».
5. Для выбранной платформы опубликованной версии используйте «Включить поддержку» / «Отключить поддержку».

Backend выбирает самую новую активную опубликованную версию отдельно для каждой платформы. Минимального порога
и редактируемых диапазонов нет. Старые активные версии могут продолжать работу.
Отключённые и неизвестные версии должны перейти на целевую.

Для отката включите предыдущую версию и отключите все более новые. Например,
после отключения 3 при активной 2 пользователи 3 получают обязательный откат на 2.
Последнюю активную версию каждой платформы отключить нельзя. Для безопасного отката проверьте
совместимость настроек и локальных данных, а также работу старого клиента с backend.

## Отдельные комплекты платформ

Архив содержит одну версию для одной или нескольких платформ: `win-x64`,
`osx-x64`, `osx-arm64`. Windows можно загрузить отдельно от macOS. Обе архитектуры
macOS допускаются вместе или по отдельности. Недостающую платформу той же версии
можно добавить позже. Уже загруженная пара «версия + платформа» неизменяема;
пересекающиеся комплекты отклоняются целиком. Новые платформы всегда черновики,
даже если другая платформа этой версии уже опубликована.

Статус публикации и поддержки хранится для каждой платформы. Описание остаётся
общим для версии; при добавлении платформ сохраняется ранее введённое описание.
Корзина действует на целый неопубликованный релиз. Если хотя бы одна платформа
опубликована, версия и её файлы сохраняются для истории и выданных предложений.
Старые общие архивы и старые записи хранилища читаются без потери публикации.

Максимум архива — 1 ГБ; распакованного содержимого — 2 ГБ. Только обычные уникальные
файлы в корне, без папок и символических ссылок. В `release.json`:

```json
{
  "version": "1.0.5",
  "notes": "Описание изменений",
  "installers": {
    "win-x64": "RevEx.Desktop-win-x64-Setup.exe",
    "osx-x64": "RevEx.Desktop-osx-x64-Setup.pkg",
    "osx-arm64": "RevEx.Desktop-osx-arm64-Setup.pkg"
  }
}
```

В `installers` перечисляются только платформы этого архива. Для каждой нужны
установщик, полный `.nupkg` и `releases.<platform>.json`. Backend проверяет
комплект, SHA256, размер, идентификатор приложения, версию, rid и канал пакетов.
При включении платформы контрольные суммы проверяются повторно.

Опубликованную версию нельзя перезаписать или удалить: пакеты нужны для истории,
откатов и уже выданных предложений. Описание редактируется отдельно от пакетов.
Черновики можно перемещать в корзину и восстанавливать.

Публичный `GET /api/desktop-installers` возвращает последние активные установщики
для каждой платформы с её версией в `targets`. Страница загрузки показывает версии
рядом с соответствующими кнопками; единой общей целевой версии больше нет.

## Протокол нового десктопа

До входа клиент отправляет версию, платформу, постоянный идентификатор установки
и её случайный ключ в `POST /api/desktop-updates/check`. Backend возвращает:

- `current` — «Да»: версия совпадает с целевой, продолжить запуск.
- `optional` — «Пока пойдёт»: версия активна, предложить переход и разрешить отказ.
- `required` — «Нет»: версия отключена или неизвестна, перейти либо закрыть приложение.

Для двух последних решений ответ содержит предложение с ID, конкретный полный
пакет, его SHA256 и размер, адрес скачивания и направление перехода для Velopack.
Клиент не выбирает релиз из feed. Предложение хранится в PostgreSQL и не меняется
при последующем переключении активных версий.

Скачивание выполняется по `GET /api/desktop-updates/offers/{id}/package` с заголовком
`X-RevEx-Installation-Key`. Поддерживается Range. Ключ не включается в URL или
административную историю. Клиент проверяет размер и SHA256; HTTP-перенаправления
для его запросов отключены.

Перед установкой клиент сохраняет ID предложения вне каталога приложения.
После перезапуска передаёт фактически запущенную версию и ID предложения.
Backend подтверждает переход только при совпадении версии и платформы пакета.
Повторное подтверждение не создаёт нового события. Ошибку установки или отмену
клиент сообщает отдельно; после неудачного перезапуска также сообщает, что
назначенная версия не установлена.

После входа клиент вызывает `POST /api/desktop-updates/report` с bearer-токеном.
Backend получает пользователя из проверенного токена и связывает его с установкой
и ранее анонимными событиями. GUID установки без её ключа не позволяет изменить
сведения. Один пользователь может иметь несколько установок с разными версиями.

Если сервер недоступен, клиент предлагает повторить проверку или закрыться.
Сбой отправки учёта после успешного входа не блокирует рабочее окно; повторная
отправка произойдёт при следующем запуске. Запуск из IDE без установки Velopack
пропускает обновления и учёт установленного клиента.

В обычных API-запросах установленный десктоп отправляет `X-RevEx-Desktop-Version`
и `X-RevEx-Desktop-Platform`. Middleware проверяет поддержку именно этой пары.
Клиенты без заголовка платформы допускаются лишь для версии, активной на всех трёх
платформах. Старый `GET /api/desktop-release` без параметра выбирает только общий
активный релиз; с `?platform=win-x64` выбирает Windows. Старые клиенты с общим
протоколом требуют ручного обновления до нового клиента, если общего активного
релиза уже нет. Новый протокол `/api/desktop-updates/check` этого ограничения не имеет.

## Хранение и учёт

Пакеты и метаданные публикации сохраняются в существующем volume `desktop-releases`,
путь задаётся `DesktopReleases:Path`. Хранилище пакетов рассчитано на один процесс
backend; для нескольких реплик нужны общее хранилище и распределённая синхронизация.

**Учёт хранится в уже существующей PostgreSQL**, с тем же подключением
`ContentHistory:ConnectionString`. Отдельный сервер БД не создаётся. При запуске
backend применяет идемпотентную миграцию под транзакционной блокировкой PostgreSQL:

- `desktop_installations` — последняя сообщённая версия, платформа, пользователь,
  время последнего обращения и хеш ключа установки;
- `desktop_update_offers` — назначенные переходы, подтверждения, ошибки и откаты;
- `desktop_downloads` — начало и результат передачи каждого файла.

В Admin → «Учёт загрузок» события отображаются в единой таблице: пользователь,
статус события, дата события и архитектура. Новые события идут сверху; доступны
поиск по пользователю, статусу, архитектуре и идентификатору установки. Источник
содержит последние 500 скачиваний и назначений обновлений. Скачивание и успешная
установка отображаются отдельными событиями. Для ошибок без сохранённого времени
дата остаётся пустой. `transferred` означает передачу полного файла сервером, `partial` —
передачу диапазона; завершение установки подтверждает клиент после перезапуска.
Прерванная работа сервера может оставить событие в состоянии «Передача начата»;
это не считается успешным скачиванием или установкой.

Время обновления — время получения подтверждения backend. Версия означает последнее
состояние, сообщённое клиентом; время обращения показывает актуальность сведений.
Пока установка не связана с авторизованным пользователем, её события анонимны.
Общедоступная первая загрузка установщика также может не иметь пользователя.

## Переход с прежнего загрузчика

Старый `/api/desktop-release` сохранён как адаптер: обе границы старого протокола
равны целевой версии, чтобы старый загрузчик установил выбранный backend релиз.
Публичные feed и пакеты опубликованных версий сохранены для этого перехода;
их передачи тоже учитываются, но прежний клиент ещё не сообщает идентификатор
установки. Новые клиенты используют предложения и не выбирают пакет из feed.

При первом запуске нового backend прежний `active.json` переносится в активность
соответствующего релиза, а исходный файл сохраняется как `active.json.legacy`.
Остальные непубликованные комплекты остаются черновиками.

Первый активный релиз нужно опубликовать до установки пользователями. Клиентам
без встроенного Velopack по-прежнему нужна первая ручная установка.

## API

Администратор:

- `GET /api/desktop-releases` — релизы, активность, публикация и корзина.
- `POST /api/desktop-releases` — multipart ZIP в поле `file`.
- `POST /api/desktop-releases/{version}/activate` — `{ "version": "1.0.5", "isActive": true, "platform": "win-x64" }`.
  Первый вызов с `true` публикует выбранную платформу; `false` отключает её поддержку.
  Без `platform` действие применяется ко всем загруженным платформам атомарно.
- `PATCH /api/desktop-releases/{version}` — изменение описания.
- `DELETE /api/desktop-releases/{version}` и `POST .../restore` — корзина черновиков.
- `GET /api/desktop-updates/history?limit=500` — учёт установок и переходов.

Десктоп:

- `POST /api/desktop-updates/check` — решение и предложение до входа.
- `GET /api/desktop-updates/offers/{id}/package` — закреплённый пакет.
- `POST /api/desktop-updates/offers/{id}/failure` — `{ "message": "..." }` и ключ установки.
- `POST /api/desktop-updates/report` — состояние после входа, требует bearer-токен.

Первичная установка и прежние клиенты:

- `GET /api/desktop-installers` — версии и ссылки отдельно по платформам.

- `GET /api/desktop-release` — целевой релиз и ссылки на установщики.
- `GET /api/desktop-releases/{version}/files/{fileName}` — опубликованные установщики и старые feed/пакеты.

## Проверки

```bash
cd Backend/RevEx
dotnet build RevEx.sln --disable-build-servers -m:1
dotnet build tests/DesktopReleaseChecks/DesktopReleaseChecks.csproj --disable-build-servers -m:1
dotnet tests/DesktopReleaseChecks/bin/Debug/net8.0/DesktopReleaseChecks.dll
```

Для проверки PostgreSQL задайте `REVEX_TEST_POSTGRES` с подключением к отдельной
тестовой базе или временной схеме: проверка создаёт реальные таблицы и события.
Не используйте рабочую схему для тестовых данных.

HTTP-проверка `tests/DesktopReleaseChecks/http-checks.mjs` использует реальные
роли Keycloak и `.env`, не выводит токены и пароли. Запускайте только против
изолированного тестового API со своим каталогом релизов, схемой PostgreSQL и базой
MongoDB. Адрес по умолчанию — `http://localhost:18082`, можно задать `REVEX_TEST_API_URL`.
Предварительно создайте ZIP-fixture:

```bash
dotnet tests/DesktopReleaseChecks/bin/Debug/net8.0/DesktopReleaseChecks.dll --write-fixture /private/tmp/revex-release-fixture.zip
node tests/DesktopReleaseChecks/http-checks.mjs
```

Fixture не является рабочим установщиком. Проверка настоящего архива CI:

```bash
dotnet tests/DesktopReleaseChecks/bin/Debug/net8.0/DesktopReleaseChecks.dll --validate-archive /absolute/path/RevEx-Desktop-Release-1.0.5.zip
```

Подпись Windows, Apple Developer ID и notarization требуют сертификатов владельца.
Реальную замену файлов и перезапуск проверяют на установленном приложении с
настоящими пакетами Velopack, включая переход вперёд и откат с сохранёнными настройками.
